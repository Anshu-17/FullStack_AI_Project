# Decision Log

## 2026-11-17 — Setup

**Stack**

| Choice | Reason |
|---|---|
| PostgreSQL (16+; 18 locally, Supabase for deployment) | Reliable relational store for companies, pages, evidence and reviews; Supabase is managed Postgres, so nothing changes at deploy time. |
| FastAPI | Typed, fast Python API with automatic `/docs` and Pydantic validation. |
| Separate background worker | Crawling and AI calls are slow; running them outside the API keeps requests fast and lets jobs resume after a crash. |
| SQLAlchemy + Alembic + psycopg 3 | Standard Python ORM, versioned migrations with downgrade, modern Postgres driver. |
| httpx + BeautifulSoup + lxml | Page downloads with timeouts/limits; robust HTML text and link extraction. |
| LangGraph (+ Postgres checkpointer) | Staged crawl → select → classify → validate pipeline whose progress is saved in Postgres. |
| LangChain connectors for Anthropic, Google, xAI | One interface for several AI providers, enabling a configurable primary provider plus fallbacks. |
| tenacity, structlog, PyJWT, bcrypt, slowapi | Retries with backoff, structured JSON logs, login tokens, password hashing, rate limiting. |
| Streamlit frontend | I'm fluent in Python, so Streamlit is the fastest way to build the UI in 24 hours. It is a separate service that calls the FastAPI backend over HTTP and **never** connects to the database directly. |
| No React / Node.js | Keeps the whole project in one language and one toolchain. |

## Stage 0 - Foundation

- **Stack:** Python 3.13 + FastAPI, PostgreSQL 16, SQLAlchemy 2 + Alembic, LangGraph (Claude / Gemini / Grok), React + Vite, Docker Compose for local dev.
- **One repository** (backend, frontend, fixtures, docs) so the evaluator can trace everything from one place.
- **One backend image, two roles:** the same Docker image runs the API (`uvicorn`) and the worker (`python -m app.worker.main`). Keeps code shared and lets us kill/restart the worker alone for the recovery demo.
- **Structured JSON logs** (structlog). Every request gets an `X-Request-ID` (reused if the caller sends one) that appears on every log line for that request.
- **Health vs readiness:** `/health` never touches the DB (is the process alive?); `/ready` checks the DB and reports the applied migration, returning **503** when not ready.
- **Requirements:** `requirements.txt` is the short, commented list of direct dependencies; `requirements.lock.txt` (pip-compile) pins everything for reproducible Docker builds. Test tools are in `requirements-dev.txt` and not shipped in the image.
- Renamed `app/logging.py` to `app/log_config.py` to avoid confusion with Python's built-in `logging` module.

## Stage 1 - Database

- **14 tables** covering intake -> work -> findings -> human review (see `backend/app/db/models.py`).
- **Integrity in the database, not just in code.** Unique constraints make these impossible even under races:
  - same website twice (`companies.canonical_domain`)
  - two jobs for one company in one run (`jobs (run_id, company_id)`)
  - two answers for one category in one job (`classifications (job_id, category)`)
  - two runs from one double-click (`runs.idempotency_key`)
  - two reviewers saving the same override version (`overrides (company_id, category, version)`) - optimistic locking
- **Statuses as strings + CHECK constraints** instead of Postgres ENUM types: easier to add values in a later migration.
- **Overrides are append-only.** The current human answer is the highest version; nothing is updated or deleted, so the full audit history is kept. `new_status = NULL` means "override removed".
- **Leases on jobs** (`lease_owner`, `lease_expires_at`, `heartbeat_at`) plus `next_attempt_at` for backoff. Partial index on running jobs' lease expiry for fast crash recovery.
- **Confidence** column documented as model self-reported, *not* a calibrated probability.
- **Pages store cleaned text (size-capped), not raw HTML**, plus a content hash. Evidence stores a short quote and a `quote_verified` flag.
- **LangGraph checkpoint tables** are created by LangGraph itself; excluded from Alembic autogenerate.
- **Seed script** creates policy `v1` and two demo users. Passwords come from `.env`, or are randomly generated and printed once - no credentials in the repo.
- **Verified:** migration upgrade -> downgrade -> upgrade on real Postgres 16; `alembic check` reports no drift; 16 tests pass (constraint tests, health/ready, password hashing).
- **Environment note:** Docker daemon was not available in the AI-assisted build environment, so `docker-compose.yml` was written but tested only by running Postgres 16, the API and the worker directly. To verify on a machine with Docker.

## Final stack decision

- **Constraint:** about 13 hours left (7 for coding with AI, 6 for docs, demo and video). I am fluent in Python, not in JavaScript, and must explain every file in the live defence.
- Compared our Python plan with an alternative Nuxt/TypeScript plan. Same architecture and requirement analysis; the difference was language. Kept Python because Stages 0-1 were already built and tested, and the alternative's Supabase-JS data access lacked transactions for safe job claiming and all-or-nothing saves.
- **Frontend: Streamlit**, a separate Python service that calls the FastAPI backend over HTTP (`API_URL`). It never connects to the database. Pure Python, with tables, upload, download and auto-refresh built in.
- React removed (not familiar enough to defend in the time available).
- **Trade-offs accepted:** less layout flexibility than React; the page script re-runs on each interaction; suited to a small team of reviewers rather than many concurrent users. A JavaScript frontend could replace it later on the same API.
- Backend requirements unchanged. Frontend has its own `requirements.txt` (streamlit, httpx) and lockfile.
- **Verified:** real FastAPI + real Streamlit run together; dashboard shows live database counts via `GET /api/stats`; UI tests cover the "backend down" message. 17 backend + 2 frontend tests pass.

## Hour 1 - Crawler

- **Design:** plain functions in `backend/app/crawler/` - `safety` (SSRF), `urls` (normalisation), `robots`, `fetch` (one page), `extract` (HTML -> text + links), `crawl` (one site), `store` (save pages). Not an API endpoint; the worker will call it. It only *collects* pages and never classifies. Page text is untrusted data and is only stored (tested with an "IGNORE ALL PREVIOUS INSTRUCTIONS..." page).
- **Limits (per website):** 8 pages, depth 2, 10 s per network operation (and per body read), 1.5 MB per page, 5 MB total, 5 redirects, 120 s deadline. Whichever is hit first is reported as `stopped_reason`. 8 pages is enough for the homepage plus the product/service/location pages that carry evidence, and keeps a 100-company run fast and cheap. Pages are fetched one at a time per site (polite); parallelism across companies is the worker's job.
- **Page priority:** a priority queue - links whose path or link text mentions our business lines (grain, agronomy, propane, feed, locations, ...) first, blog/news/careers/login/privacy last, breadth-first within a priority. Because we only take 8 pages, they should be the most useful 8.
- **robots.txt (RFC 9309):** 4xx -> allow all; 5xx, 429, timeout or unreachable -> disallow all; cached per origin for the crawl. Parsed with `urllib.robotparser` (limitation: no `*`/`$` wildcards, first-match not longest-match). Disallowed pages are recorded as `robots_disallowed`, never fetched.
- **SSRF protection:** only http/https, no `user:pass@`, and *every* IP the hostname resolves to must be public (`is_global`, IPv4-mapped IPv6 unwrapped) - blocks 127.x, 10.x, 172.16-31.x, 192.168.x, 169.254.169.254, ::1. Redirects are followed by hand and every hop is re-checked. `CRAWL_ALLOWED_PRIVATE_HOSTS` allows local test fixtures and is ignored in production. **Known limitation - DNS rebinding:** we resolve, then httpx resolves again when connecting; re-checking every hop narrows the window, full IP pinning is future work.
- **Fetch robustness:** never raises - every problem becomes a `PageOutcome`. 4xx is final; 429/5xx/timeouts are retried twice with exponential backoff + jitter, honouring `Retry-After` up to a 4 s cap. Bodies are streamed and cut off at the size limit (the declared `Content-Length` is not trusted). Only `text/html` is accepted.
- **No JavaScript rendering (limitation):** we read the HTML the server sends. Sites that build their content in the browser will return little text; those pages show up with short text and can be flagged for review. A headless browser was rejected as too heavy and too risky for this time box.
- **Storage:** cleaned text only (max 50,000 chars per page; block elements become lines, inline whitespace collapses so quotes can be matched later), plus a SHA-256 of the text. `(job_id, url)` stays unique: a retried job *updates* its page rows (Postgres upsert) instead of duplicating them. NUL characters are stripped (Postgres rejects them).
- **Verified:** 112 backend tests pass (17 existing + 95 new: urls 32, safety 19, fetch 16, crawl 12, robots 6, extract 6, store 4); HTTP faked with respx, DNS faked - no real network in tests. Real-site check with the CLI: agtegra.com 8/8 pages ok (products-services, agronomy, energy, feed, grain, locations; 20 s), insightfs.com 8/8 ok (3 s).
- **Observed on real sites (follow-ups):** (1) insightfs.com redirects to `fscooperatives.com/insightfs`, a shared site for several FS co-ops; the crawler then treats the whole `fscooperatives.com` as the company site, so pages of *other* co-ops could be collected. Fix candidate: after a cross-domain homepage redirect, stay under the redirect's path prefix. (2) Navigation menus repeat at the top of every page's text; removing `<nav>/<header>/<footer>` would give cleaner evidence.

## Hour 2 - Classifier

- **Crawler follow-ups fixed first:** (1) after a cross-domain homepage redirect (insightfs.com -> fscooperatives.com/insightfs) the crawler stays under the target path and records `redirected_to`; sibling paths of a shared site are never crawled. (2) `<nav>` and `<header>` are removed from page text (menu noise) while their links are still followed; `<footer>` is kept because addresses and opening hours are retail-store evidence.
- **LangGraph dropped:** the pipeline is plain staged Python functions (select -> prompt -> call -> validate -> save). Simpler to read and explain, and still a reproducible staged pipeline: versioned prompt and policy, deterministic passage selection, every AI call logged. `langgraph` and `langgraph-checkpoint-postgres` removed from requirements; `langchain-openai` added (Groq).
- **Providers:** Gemini (`gemini-2.5-flash`) primary, Groq (`openai/gpt-oss-20b`) fallback through Groq's OpenAI-compatible API, so no extra package. Anthropic/xAI/OpenAI are wired but unused. A provider is used only if both its key and model are set. Temperature 0; each client's own retries are disabled so every attempt is ours and visible in `ai_usage`.
- **Passage budget:** pages are split into ~400-character passages, scored per category by keyword hits; the homepage's first passage plus the top 5 per category (round-robin) are sent, capped at 12,000 characters (~3-4k input tokens). Controls cost and free-tier rate limits; deterministic, so a run is reproducible.
- **Prompt security:** website text is untrusted. It is sent only inside `<untrusted_website_content>` tags in the user message (a page cannot close the tag early - it is neutralised), and the system prompt says to treat it as data. We do not rely on the model obeying: validation below is what protects the result.
- **Validation (trust nothing from the model):** all 6 site categories exactly once (else retry); every quote must be verbatim in the cited passage AND in the stored page text (whitespace/case-insensitive) or it is dropped; `yes`/`possible` with no verified quote becomes `not_found`; a `yes` whose quotes contain none of the category's keywords becomes `possible` (simple relevance heuristic); any downgrade, dropped quote, `possible` or override conflict sets `review_required`. Accounting is never sent to the AI: `yes` by business rule, provenance `rule`.
- **Size limits enforced per quote, not per answer:** on a real run, one 370-character quote made Gemini's otherwise good answer fail the schema three times. Limits (quote 10-300 chars, max 3 quotes, explanation 400 chars) are now told to the model and enforced in validation per item; wrong categories/statuses still reject the answer.
- **Prompt p2:** real runs showed models stitching separate fragments into one "quote" (with "..." or skipped words). The prompt now requires one continuous span; stitched quotes are still caught and dropped by validation.
- **Retry / fallback:** per provider up to 3 attempts with exponential backoff + jitter (tenacity), honouring Retry-After / Gemini's "retry in Ns" up to 10 s, for timeouts, 429, 5xx and invalid output. A bad key (`AI_AUTH`) or unknown model (404) is not retried - straight to the next provider. All providers failing -> `AI_UNAVAILABLE`, no classifications saved. No usable crawled text -> `NO_CONTENT` (a crawl failure, not "not found" x6), no AI call.
- **Human overrides:** the latest override per category (highest version, non-removed) is compared with the new automated status; a difference sets `conflicts_with_override` and review. Override rows are never changed.
- **Cost recording:** tokens and latency for every call in `ai_usage`; `est_cost_usd` only when prices are configured (`AI_PRICE_*_PER_MTOK`), otherwise NULL ("unknown") - never invented. One price pair applies to all providers (simplification).
- **Data note:** Gemini's free tier may use requests to improve Google's products. We only send public website text (no personal or customer data).
- **Verified:** 148 backend tests pass (fake chat model, no network); real runs on agtegra.com: Gemini primary - all 6 site categories `yes` with verified quotes (cardlock fuel stations, farm stores, feed, propane, cash bids); forced fallback (`GOOGLE_MODEL=does-not-exist` for one command) - one `AI_ERROR` row for Google, then Groq `ok`.
- **Known limitations:** keyword relevance check is a heuristic (word-start matching; can be fooled or be too strict); confidence is model self-reported; quotes spanning two passages cannot verify; classifications for a job cannot be saved twice (unique per job/category) - the worker must not re-classify a finished job; Gemini 2.5 Flash "thinking" tokens are counted as output tokens.

## Hour 3 - API and worker

- **Endpoints (all under `/api`, no auth yet):** `POST /uploads` (CSV), `GET /uploads/{id}/rows`, `POST /companies`, `GET /companies` (final answers + latest job + last scanned), `GET /companies/{id}` (answers with evidence, scan history), `POST /companies/{id}/rescan`, `POST /runs`, `GET /runs`, `GET /runs/{id}`, `GET /runs/{id}/items`, `POST /runs/{id}/cancel`, `POST /runs/{id}/retry-failed`, `GET /jobs/{id}`, `POST /jobs/{id}/retry`, `GET /stats`, `GET /metrics`. Every error is `{"error": {"code", "message", "details"}}` (422 lists bad fields); every list is `{"items", "page", "page_size", "total"}` (page_size max 200). The API never crawls or calls the AI: requests return in milliseconds, the worker does the slow work.
- **Ingest:** CSV max 2 MB / 5,000 rows, UTF-8 with or without BOM, headers case/space-insensitive. Each row is `accepted`, `existing` (linked), `duplicate` (names the earlier row) or `invalid` (with a reason). Companies are inserted with `INSERT ... ON CONFLICT (canonical_domain) DO NOTHING` then selected, so two simultaneous uploads of the same company make one row and no error (tested with two threads). 1,000 rows ingest in about a second.
- **Idempotency:** `POST /runs` with an `Idempotency-Key` header returns the SAME run (200) when the key was seen before; the key is UNIQUE in the database, so even two simultaneous requests create one run. Duplicate company ids collapse.
- **"Skip if already in progress":** a company with a queued/running job in any run is skipped and listed as `already_in_progress` (409 `NOTHING_TO_RUN` if nothing is left). Backed by a new partial unique index (migration `9633adfef360`): at most one queued/running job per company, so a race between two requests cannot slip through.
- **Final answers ("human override wins"):** automated answers come from the company's latest finished job; the latest override with a status wins with provenance `human`; the automated answer and evidence are returned alongside and `conflict` shows disagreement; never-scanned categories are `null` ("not scanned yet"), not `not_found`.
- **Leases:** a worker claims a job with `SELECT ... FOR UPDATE SKIP LOCKED` (two workers can never take the same job and neither waits for the other), sets `lease_owner` and `lease_expires_at = now() + 120 s`, and a heartbeat thread renews it every lease/3. All times use the database clock. `recover_expired_leases` (run before every claim) turns an expired lease into an `abandoned` attempt and re-queues the job, or fails it with `WORKER_LOST` when no attempts are left.
- **Fencing before finalize:** saving the 7 classifications + evidence, the job's final status, the attempt result and the job event happen in ONE transaction that first locks the job row and checks it is still `running` with `lease_owner = me`. If the lease was lost (taken over after expiry), nothing is saved and `LEASE_LOST` is logged. The unique `(job_id, category)` rule is the second safety net. The same check guards retries, failures and cancels.
- **Retry policy:** permanent errors (`INVALID_URL`, `BLOCKED_UNSAFE`) fail at once. Retryable ones (`NO_CONTENT`, `AI_UNAVAILABLE`, unexpected `INTERNAL_ERROR`) go back to the queue with `next_attempt_at = now + min(300, 10 * 2^(attempt-1)) s + 0-25 % jitter` (10 s, 20 s, 40 s, ...), until `max_attempts` (3) is reached. Manual retry gives a failed/cancelled job a fresh budget (`max_attempts = attempt_count + 3`) and keeps the attempt history.
- **Reuse on retry:** if an earlier attempt already saved `ok` pages for the job, the retry does not crawl again (seen in scenario A).
- **Cancel:** queued jobs are cancelled at once; the run becomes `cancelling` while jobs are running; the worker checks for a cancel before crawling and again before classifying and then finishes the job as `cancelled` with no classifications; when nothing is running the run is `cancelled`. Finished jobs are untouched. Retrying a job of a cancelled run clears the cancel flag.
- **Run status** is always recomputed from its jobs (locking the run row so two finishing workers can't compute from stale counts): any queued/running -> `running` (`cancelling` if cancel requested); all finished -> `completed`, `completed_with_errors`, `failed` or `cancelled`. Progress = finished jobs / total, from the database.
- **Lock order** (no deadlocks): worker locks job -> run; claim commits the job before touching the run; cancel / retry-failed lock run -> only queued/failed jobs, which a worker never holds.
- **Single process, threads - not distributed:** one worker process runs `WORKER_CONCURRENCY` threads (default 2, free-tier AI limits). Several worker processes or machines would already work correctly (SKIP LOCKED claims, leases and fencing live in Postgres); a real multi-worker deployment would still need per-provider rate limiting shared between workers, a supervisor to restart crashed workers, and metrics per worker.
- **Shutdown:** SIGINT/SIGTERM stops claiming and waits up to 30 s for jobs in progress; a hard kill is also safe (scenario A: lease expired, attempt abandoned, job finished by another worker with exactly 7 classifications).
- **Production safety:** with `ENVIRONMENT=production` the app refuses to start if `JWT_SECRET` is missing, `change-me` or shorter than 32 characters.
- **Verified:** 200 backend tests pass (incl. two concurrent claimers, two concurrent ingests, lease recovery, lease stolen before finalize, cancel between crawl and classify, AI unavailable -> backoff -> failed, run status for every combination). Live: scenario C (`docs/evidence/scenario_C_duplicates.md`) and scenario A with a hard `taskkill /F` (`docs/evidence/scenario_A_worker_crash.md`).
- **Known limitations:** an AI call in flight when a worker is killed is not recorded in `ai_usage` (usage is written after the call); `ai_usage.created_at` is the transaction start time, not the call end; the company list filters by final answer in Python (fine for thousands of companies, not millions); job duration in metrics runs from first claim to finish (includes retry waits); a manual retry is refused (409) if the company already has another active job; no authentication yet (Hour 5).

## Hour 4 - Auth, corrections, export, UI

- **Login (JWT):** `POST /api/auth/login` checks the bcrypt password hash and returns an HS256 token signed with `JWT_SECRET` (claims: `sub` = user id, `role`, `exp` after 480 min). Wrong email and wrong password get the same 401 "Invalid email or password." (a dummy hash is checked for unknown emails so the timing doesn't leak either); inactive users get the same 401. The role and active flag are re-read from the database on every request, so disabling a user or changing a role works immediately.
- **Roles and what is protected:** open: `/health`, `/ready`, `/docs`, `/openapi.json`, `POST /api/auth/login`. Every other `/api` route needs a logged-in user (viewer or reviewer). Every change needs a reviewer (403 "Reviewer role required."): uploads, add company, rescan, start/cancel/retry runs and jobs, corrections. Viewers can read and export. Errors keep the `{"error": {...}}` shape (401 / 403 / 429).
- **Rate limits (slowapi, per client IP):** login 10/minute, uploads 20/minute, everything else 300/minute; 429 `RATE_LIMITED`. Counters are in the API process's memory (reset on restart, not shared between several API processes - a shared store such as Redis would be needed for that).
- **Corrections with optimistic locking (scenario G):** each correction of (company, category) gets the next version; the UI sends the version it displayed as `expected_version`. A different current version -> 409 `VERSION_CONFLICT` with who changed it, when, and the current answer. Two saves at the same instant both pass that check but the UNIQUE `(company_id, category, version)` rule lets only one insert win; the other gets the same 409. Corrections are append-only (`new_status = null` removes a correction and returns to the automated answer), so the full history is kept. A human may correct Accounting too; the AI never can.
- **"Human wins" display (scenario E):** the final answer is the latest correction if there is one (provenance `human`), else the latest finished scan (`site` or `rule`), else "not scanned yet" (null, never "not found"). The automated answer and its evidence are always shown alongside; a new scan that disagrees is saved with `conflicts_with_override = true` and the UI shows "⚠ Conflicts with the latest automated scan". Verified live: correction to Possible, rescan said Yes, final answer stayed Possible (human), override row unchanged.
- **Exports:** `GET /api/exports?format=csv|json` with the same filters as the company list. CSV: one row per company, and per category `status, source (site/rule/human), evidence_url, quote (first verified, trimmed to 300 chars), conflict`. JSON: everything (final answers, automated answers with all verified evidence, model / prompt / policy versions, correction history). `GET /api/exports/overrides` = the audit trail. Dated file names (`companies-YYYY-MM-DD.csv`). The data is read inside the request and then streamed out.
- **Timestamps:** all database sessions use `TimeZone=UTC`, so the API, UI and exports show `+00:00` times whatever the server's time zone.
- **Streamlit structure:** `app.py` (login gate + navigation + sidebar with user, role, logout, backend URL, source legend), `api_client.py` (the ONLY place that calls the backend; adds the Bearer token; on a 401 for a logged-in user it logs out and shows "Your session expired, please log in again."), `ui.py` (status / source badges, labels, error and loading helpers), and one file per page in `views/`: login, dashboard, add companies (single form, CSV upload with rejected-rows table and a sample CSV, "Start research" with one Idempotency-Key per upload kept in the session so a double click can't make two runs), companies (search, category/status filters, paging, export buttons), company detail (7 answers with badges, evidence, versions, conflict note, reviewer correction form, histories, rescan), runs (server progress, items with errors, cancel / retry, job drill-down). Reviewer-only controls are hidden from viewers; the backend enforces it anyway.
- **Auto-refresh:** the runs page wraps the live part in `st.fragment(run_every=3)` only while the run is queued / running / cancelling, so just that part re-runs every 3 s; when the run finishes, the page redraws once without the fragment and refreshing stops. Progress always comes from the server (finished jobs / total).
- **Verified:** 227 backend tests (auth, roles, rate limit, corrections incl. two-session race and a forced insert race, scenario E, exports) and 11 UI tests (3 consecutive runs, `default_timeout=30`, fixing the earlier flaky dashboard test). Live: viewer reads but gets 403 on changes; the real Streamlit pages driven against the live API as reviewer (7 correction forms, rescan button) and viewer (none); scenario E; exports downloaded as viewer. Evidence: `docs/evidence/scenario_E_override_conflict.md`, `scenario_G_concurrent_edits.md`, `export_sample.md`.
- **Known limitations:** the token lives only in the Streamlit session (closing the tab logs you out; no refresh tokens, no server-side revocation list - disabling the user is the way to cut access); single organisation, no multi-tenancy; no user-management screens (users come from the seed script); rate-limit counters are per API process; the company list and export filter on final answers in Python (fine for thousands of companies); the UI's "Start research" for an upload reuses one key per upload, so starting the same upload again later needs a new upload.

## Proof - fixtures, scenarios, pilot, scale

- **Test data is labelled.** Migration `13822ee21a66` adds `companies.source` (`user` / `fixture` / `synthetic`, default `user`, CHECK constraint) - an additive change with a server default, so existing rows and older code keep working (scenario J shows upgrade -> downgrade -> upgrade on `bep_test`). The API returns `source` / `is_test_data`, exports include it, the UI shows a grey "Test data" badge and a "Hide test data" filter.
- **Local fixture websites.** `fixtures/server.py` (standard library only) serves `fixtures/sites/<name>/` - 9 content sites (clear co-op, grain farm only, fuel delivery only, pet store, online catalog, outdated elevator, feed mill, cardlock fuel, prompt injection) and special ones (redirect to a private IP, robots.txt disallow-all, every page 500, empty homepage, slow page). Each fixture company has its own domain `<site>.fixture.test`; numbered copies (`clear-coop-305.fixture.test`) map to the same site for load tests. `.test` is reserved (RFC 2606) so these can never be real websites.
- **Test-only hooks, impossible in production.** No hosts-file edits: (1) `CRAWL_FIXTURE_SERVER=127.0.0.1:8765` mounts an httpx transport that sends ONLY `*.fixture.test` requests to the local server, keeping the original Host header and URL; (2) `CRAWL_ALLOWED_PRIVATE_HOSTS=*.fixture.test` lets only those names pass the SSRF check. Both are ignored when `ENVIRONMENT=production` (`fixture_routing_enabled()` / `allowed_private_hosts()` return nothing) and tested so. Redirects from a fixture to a real private IP are still blocked. (3) The `fake` AI provider (`fake-keyword-v1`: keyword-based, quotes passage lines verbatim, no network) is refused in production (`provider_order()` skips it, `build_structured_model("fake")` raises). (4) `JOB_BACKOFF_BASE_SECONDS` (default 10) only shortens retry waits for demos. All four are set in a single command's environment, never in `.env`.
- **Quote-length rule (validation, not prompt):** a `yes` needs at least one verified quote of >= 25 characters AND >= 4 words; otherwise it becomes `possible` and the job goes to review ("Feed and Nutrition" - a menu heading - is verified text but not evidence). Prompt and policy versions were not changed for this rule.
- **Prompt p3:** the fixture evaluation (and live scenario H) showed the model answering `not_found` for "our elevator closed in 2015"; the brief says outdated evidence is `possible`. p3 adds one explicit instruction. Because p3 was written after seeing that miss on the same fixture set, the evaluation's 54/54 measures fit to our 9 synthetic sites, not real-world accuracy (no held-out set).
- **Evaluation method:** `scripts/evaluate.py` ingests the labelled fixtures (`source=fixture`), runs the REAL pipeline (crawl -> Gemini/Groq -> validation) through the normal worker code, and compares the automated answers with `sample-data/labelled_fixtures.csv`: precision / recall per category (positive = `yes`), confusion tables, exact match, and every yes/possible quote for a manual audit. The real-world quality signal is the manual audit of the 15-company real pilot (78 quotes: 66 OK, 9 weak, 3 questionable; 2 clear false negatives, both from the Groq fallback model).
- **Scale checks:** 1,000-row intake in one request in ~1.4 s (900 / 50 duplicates / 50 invalid, every row with a reason); 100 synthetic jobs with fixtures + fake AI: ~70 jobs/min on 2 threads, exactly 7 answers per successful job, 0 duplicates, broken-site jobs retried twice then `NO_CONTENT`.
- **Limitations found by the proof work:** Gemini's free tier allows 20 requests/model/day - it ran out during the pilot; there is no circuit breaker that skips a provider for the rest of the day (each attempt still tried Gemini 3 times); Groq's `gpt-oss-20b` made the two clear errors and sometimes hits its output-token limit; a site whose TLS chain Python cannot verify is recorded as `robots_disallowed` (robots.txt unreachable) - misleading label; pages with identical text are crawled twice and waste the 8-page budget; two real sites return 403 to any crawler; job latency in the synthetic test excludes ~1 s per job of loop overhead that is not yet explained. The fixture set is small, hand-written and was used to tune the prompt - not a measure of real accuracy.

## Fixes from the pilot

- **Provider quota breaker:** an AI error that says the DAILY quota is used up (Gemini `...PerDay...` / "per day"; Groq "tokens/requests per day (TPD/RPD)") becomes `AI_QUOTA_EXHAUSTED`: not retried, and the provider is skipped by this worker process for `AI_QUOTA_COOLDOWN_SECONDS` (default 1800 s). Skips are logged (`ai.provider_skipped_quota`) and recorded as `ai_usage` rows with outcome `skipped_quota` (no tokens), so the waste seen in the pilot (85 calls to an exhausted Gemini) can't recur. Ordinary per-minute 429s keep the normal backoff and retry. In memory and thread-safe (a lock); a restarted worker simply finds out again with one call.
- **Groq fallback:** default model `openai/gpt-oss-120b` (stronger than 20b; also set in `.env`). Every provider is created with `max_tokens = AI_MAX_OUTPUT_TOKENS` (default 8192 - more than the brief's 4096 example because Gemini 2.5's hidden "thinking" used ~1,800 of ~3,500 output tokens on real sites). A cut-off answer (`finish_reason` length / MAX_TOKENS, or the OpenAI SDK's `LengthFinishReasonError`) is `AI_INVALID_OUTPUT` and retried, never accepted.
- **Duplicate-text pages:** a page whose text hash equals an earlier page in the same crawl is kept as `ok` with `error_detail = "duplicate_of:<url>"`, does not count toward the 8-page budget, its links are not followed again, and passage selection skips it (it is never sent to the AI).
- **Gemini model check (2026-11-18 14:15 UTC):** 2.5-flash, 2.5-flash-lite and 3.5-flash all answered a one-word test call (the daily quota had reset). The free-tier limit is per model per day, so the model choice changes which daily bucket is used.

## Deployment setup (Render + Supabase)

- **Target:** Supabase Postgres + two free Render Docker web services from `render.yaml` (`bep-api`, `bep-ui`). Step-by-step in `docs/deployment.md`.
- **One container = API + worker** (`backend/start.sh`: migrations, seed, worker in a background restart loop, uvicorn in the foreground on `$PORT`). Honest trade-off: free Render web services sleep when idle and background workers aren't free, so the worker sleeps with the API; production would run them as separate always-on services. `docker-compose.yml` still runs them separately locally.
- **Database URL:** the Supabase **session pooler** string (port 5432) can be pasted as shown; config turns `postgres://` / `postgresql://` into `postgresql+psycopg://` and adds `sslmode=require` for Supabase hosts. psycopg's automatic prepared statements are disabled for pooler hosts (and port 6543) so a transaction-pooler URL can't break queries. UTC is now set with `SET TIME ZONE 'UTC'` on each new connection instead of a startup option (poolers may reject startup options).
- **Production safety:** the seed REQUIRES `SEED_REVIEWER_PASSWORD` / `SEED_VIEWER_PASSWORD` when `ENVIRONMENT=production` and never generates or prints passwords there; worker concurrency defaults to 1 in production unless `WORKER_CONCURRENCY` is set; fixture routing, the private-host allowlist and the fake AI provider stay off in production (tested); weak `JWT_SECRET` still refuses to start.

## Stay logged in on refresh + polished UI (2026-11-18)

- **Problem:** the token lived only in `st.session_state`, so a browser refresh (a new Streamlit session) logged the user out.
- **Fix:** the JWT is also kept in a browser cookie `bep_token` (`frontend/browser_session.py`): read with `st.context.cookies` on the first run of a session, written / deleted with `extra-streamlit-components`' CookieManager (pinned 0.1.81, MIT; lockfile regenerated). Secure on https, SameSite=Strict, Path=/, Max-Age = `expires_in`; never in the URL. On load: `GET /api/auth/me` -> logged in, or 401 -> cookie deleted + "Your session expired". Logout deletes the cookie and marks the session so the stale cookie the browser sent at page load can't log it in again. Login / logout only queue the cookie change; `app.py` applies it on the next normal run (an immediate `st.rerun()` would remove the cookie component before its JavaScript runs).
- **Trade-off (accepted for the prototype):** a cookie written by page JavaScript cannot be HttpOnly, so a script on the page could read it. Mitigated by the 8 h expiry, Secure, SameSite=Strict, no URL tokens and escaping all website text; a production app would use an HttpOnly server-set session cookie with server-side revocation. Documented in `docs/design.md` (security).
- **Polished UI:** theme in `frontend/.streamlit/config.toml` (deep green / warm neutral, sans-serif, rounded corners); shared CSS + header (app name, subtitle, user / role chip, page description) in `frontend/ui.py`; dashboard metric cards; colour-coded Companies table (pandas Styler); company header card + 7 category cards (status / source badges, quotes as blockquotes with source and fetch time, amber conflict callout, correction form in an expander); run progress with count pills and failed jobs highlighted with their error; centred login card. Every text / badge colour pair was computed at >= 6.4:1 (WCAG AA needs 4.5:1).
- **Security note:** the UI now builds some HTML itself, so every website-derived string goes through `ui.esc()` (HTML-escaped) - tested with a quote containing `<img onerror>`.
- **Checked:** 22 frontend tests (4 new for the cookie: refresh stays logged in, expired -> login, logout deletes, login saves with the token lifetime; 1 for escaping), 3 runs; screenshots at 1366 px and 390 px (phone) in `docs/evidence/ui_screenshots/`, taken with Playwright + Edge against the local API (a login token for the local reviewer was created in-process for the screenshots and deleted afterwards - no password used or shown).
